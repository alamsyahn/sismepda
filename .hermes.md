# Hermes Workflow for SISMEPDA

`docs/README.md` is the canonical system map. Documentation in `docs/`
represents the current system state and durable project knowledge.
Git history records historical changes.

These rules apply to EVERY task affecting this project, even when the user's
prompt does not mention documentation.

The user does not need to say "read the docs" or "update the docs".

## Mandatory workflow

For every normal task:

1. Read `docs/README.md` and ALL canonical documentation relevant to the task,
   including related active technical debt.
2. Use documentation as the system map. Do not rediscover the project from
   source code.
3. Inspect only the source, tests, schema, configuration, logs, and data
   directly needed for the task and its direct dependencies.
4. Implement only the requested scope. Do not fix unrelated issues or debt.
5. Run validation appropriate to the change.
6. ALWAYS review the affected canonical documentation after implementation.
7. Update existing canonical docs whenever durable system knowledge changed.
8. Review/update related technical debt.
9. Remove docs that became obsolete, duplicated, contradictory, or fully
   superseded.

Normal workflow:

DOCS → TARGETED CODE → IMPLEMENT → VALIDATE → DOCS REVIEW/UPDATE

Documentation review is mandatory for every task.

If no durable knowledge changed, do not make artificial documentation edits;
confirm that the relevant canonical docs were reviewed and remain accurate.

## Documentation rules

Update existing canonical documents by default.

Before creating a new document, check whether an existing canonical document
already owns that knowledge.

Create a new document only for a genuinely new durable feature, subsystem,
architectural concern, or operational procedure.

Do not create task reports, implementation summaries, fix notes, changelogs,
historical docs, duplicate docs, `*-v2`, `*-new`, or `*-final` documents.

Documentation describes how the system works NOW. Git history is the archive.

When replacing old documentation:
1. migrate still-valid knowledge;
2. update references;
3. remove the obsolete/superseded document.

## Database operations

Before any database operation, read `docs/operations/local-database-workflow.md`.

The production database is READ-ONLY from development workflows. Never run
migrations, seeds, resets, backfills, test scripts, or destructive SQL against
production.

`sismepda_prodclone` is the disposable local clone of production.

`sismepda_dev` is the persistent local development database and must not be
destroyed unless explicitly requested.

Select the target with `npm run dev:local` or `npm run dev:prodclone`; never
switch by editing `.env` by hand.

## Technical debt

Active technical debt lives in `docs/technical-debt/README.md`.

Record only verified, unresolved engineering liabilities.
Do not treat feature requests, wishlists, cosmetic improvements, or speculative
concerns as technical debt.

Do not automatically fix unrelated debt.

Update an existing debt entry instead of duplicating it.
When its exit criteria are verified, remove the resolved entry.

## Full-system inspection

A repository-wide audit, architecture rediscovery, broad source scan, full
dependency inspection, or full database inspection is NOT part of normal work.

Only perform full-system inspection when the user explicitly requests it,
for example:

- "inspect keseluruhan sistem"
- "lakukan full system audit"
- "analisis seluruh codebase"

Unexpected errors do not authorize full inspection.

Investigate them locally using relevant docs, targeted source, direct
dependencies, tests, logs, configuration, and data.

If that is insufficient, report that a separate full-system inspection may be
needed. Do not start one automatically.

## Git completion policy

For every normal task:

1. Before making changes, inspect the current Git working tree with `git status`.
2. Never discard, overwrite, reset, or include unrelated pre-existing changes.
3. After implementation and validation, review the final diff and ensure only changes belonging to the current task are included.
4. Do not stage with `git add .` or `git add -A` when unrelated changes may exist. Stage only the files that belong to the current task.
5. Never commit secrets, credentials, database dumps, local environment files, generated local artifacts, or unrelated changes.
6. If the task is successfully completed and its required validation passes, create one descriptive local Git commit containing only that task.
7. If validation fails or the task is incomplete, do not create a completion commit merely to make the working tree clean.
8. Leave the working tree clean when possible after a successful task.
9. Never push, pull, reset, rebase, force-push, merge, deploy, or modify production unless explicitly requested by the user.
10. If unrelated pre-existing changes make a safe isolated commit impossible, preserve them and report the situation instead of committing or removing them.

Normal completion flow:

IMPLEMENT
→ VALIDATE
→ DOCS REVIEW/UPDATE
→ REVIEW DIFF
→ STAGE TASK-SPECIFIC CHANGES
→ COMMIT LOCALLY
→ STOP

The default stopping point is a local commit.
Pushing or deploying always requires an explicit user request.

## Non-negotiable

Even for prompts such as:

"fix this"
"update this code"
"add this field"
"change this behavior"

you MUST still follow:

READ RELEVANT DOCS
→ TARGETED INSPECTION
→ IMPLEMENT
→ VALIDATE
→ REVIEW/UPDATE DOCS

Do not skip documentation because the user forgot to mention it.
